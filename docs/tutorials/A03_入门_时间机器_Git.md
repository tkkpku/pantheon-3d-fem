# 入门第 2 课 · 时间机器：给你的每一步存档

> 写给：只在「另存为副本.docx」时代存过档的学生。
> 承诺：读完这篇，你能用四条命令管理一个项目的一生，并且永远不会再问「我上次改了什么」。
> 前置：无（独立成课）。

---

## 先给一张地图

Git 干的事只有一件：**给你的项目拍快照，而且每张快照都能随时还原。**

不用 Git 的项目是这样存活的：`论文_v1.docx` → `论文_v2.docx` → `论文_v2_最终版.docx` → `论文_v2_最终版_真的.docx`。文件名越滚越长，而你想回到「删掉第三章之前」的样子——回不去了。

Git 的做法：每次你说「存一下」，它拍一张**全项目快照**，附一句你写的说明（比如「删掉了第三章」）。想回到任何一张快照，一条命令。**这就是全部魔法。** 剩下的都是操作细节。

---

## 第 1 节 三棵树：工作区、暂存区、仓库

Git 有三个「地方」，新手晕 Git 九成是没分清它们：

| 地方 | 比喻 | 你的动作 |
| --- | --- | --- |
| 工作区 | **你的书桌**——正在改的文件 | 随便写随便改 |
| 暂存区 | **打包台**——决定哪些文件进这张快照 | `git add 文件名` |
| 仓库 | **档案柜**——快照存放处 | `git commit` |

**关键**：改完文件 ≠ 存档。完整的存档动作是**两步**：先 `git add`（把文件放上打包台），再 `git commit`（打包进档案柜）。漏掉任何一步，你的修改都还没「存档」。

▢ **你试试 1**：在你自己的任意文件夹里，`git init` 建一个仓库，新建一个文件写两行字，然后 `git add .` + `git commit -m "第一次存档"`。改一行字，再 `git status`——看它怎么告诉你「有文件被改过但还没打包」。

⚠️ **新手常犯**：只 commit 不 add（快照里没有你的修改），或只 add 不 commit（永远停在打包台上）。**口诀：改→add→commit，三步才算存了档。**

## 第 2 节 一句话说明：commit message 是写给谁的

每次 commit 要写一句话说明。万神殿项目的规矩（也应该是你的）：

```
feat(geo): C3 圆角藻井 --round 开关与 P-09 诊断留档
docs: 万神殿全解成书 15 卷
fix: 修复密度分层方向写反
```

- **feat** = 新功能；**fix** = 修 bug；**docs** = 只动文档；
- 括号里是范围（geo=几何、fem=求解）；
- 冒号后面一句话说清干了什么。

**这句话是写给三个月后的自己**：那时你完全不记得今天在干嘛，但 `git log` 一翻——33 句话就是项目的一生。万神殿 8/17 决战日一天 16 条 commit，把「上午标定参数→下午攻坚网格→晚上闭环结论」的战役写得清清楚楚，这就是榜样。

▢ **你试试 2**：打开万神殿仓库跑 `git log --oneline`，读最近 10 条 commit。找一找 feat/fix/docs 三种前缀各出现几次，感受「一句话讲清一件事」的密度。

⚠️ **新手常犯**：写「update」「改了点东西」这种废话。**commit message 的标准：三个月后的陌生人只读这一句，能不能知道这次改了什么。** 能 → 合格。

## 第 3 节 三棵树的反向操作：撤销

Git 最值钱的能力是「反悔」，三个层次的撤销对应三个地方：

| 场景 | 命令 | 白话 |
| --- | --- | --- |
| 改乱了工作区，想回到上次 commit 的样子 | `git restore 文件名` | 把书桌恢复成档案柜里的样子 |
| add 错了文件 | `git restore --staged 文件名` | 从打包台上拿下来 |
| commit 写错了说明 | `git commit --amend` | 重写上一张快照的说明 |

**万神殿项目的神仙操作**：`git -c safe.directory="..."` 临时绕过权限检查（沙箱用户和真实用户不是同一个身份时 git 会拒绝读仓库）。**记住：永远用 `-c safe.directory` 单命令绕过，不要写进全局配置**——全局配置是给全世界开的后门。

▢ **你试试 3**：改乱一个文件，用 `git restore` 救回来。**先备份再试**——撤销命令本身也可能操作错，练手时拿不重要的文件练。

## 第 4 节 什么该存档，什么不该：.gitignore

不是所有文件都值得进档案柜。万神殿项目的规矩（写在一个叫 `.gitignore` 的文件里）：

**该存**：代码、文档、参数表——**「删了它，项目就死了」的东西**。

**不该存**：输出结果、网格文件、缓存——**「删了它，跑一遍脚本就回来」的东西**。万神殿的 15 个网格文件几百 MB，全存进 git 仓库会把它撑爆，而且毫无意义：网格是用 geometry 脚本生成的，脚本才是资产。

**判据一句话**：这个文件删除后，能不能用仓库里已有的东西重新生成？能 → 不进 git。

▢ **你试试 4**：打开万神殿根目录的 `.gitignore`，读每一条注释，把「output/」「__pycache__/」「legacy_v1/」三条各自归入「可重新生成」或「资产」两类。

⚠️ **新手常犯**：把密钥、token 写进代码然后 commit——**一旦进档案柜就永远留在历史里**，删都删不干净。万神殿纪律：密钥只在环境变量和本地凭据文件里，永不入库。

## 第 5 节 万神殿的真实 git 病历（三个坑）

| 坑 | 症状 | 解法 |
| --- | --- | --- |
| dubious ownership | git 拒读：「fatal: detected dubious ownership」 | 沙箱身份与文件属主不同 → `git -c safe.directory=...` 单命令绕过 |
| 文档里的隐形字符 | 索引文件某行「看起来正常但 grep 不到」 | 被写入了 NUL 空字节 → 重写该行（AI 产出文档要抽查） |
| 嵌套仓库 | legacy_v1 里有自己的 .git | 父仓库 .gitignore 排除它 + bundle 备份，互不干扰 |

## 第 6 节 本课复习卡

| 概念 | 一句话 |
| --- | --- |
| 快照 | commit = 全项目存档 + 一句说明 |
| 三棵树 | 工作区（书桌）→ add → 暂存区（打包台）→ commit → 仓库（档案柜） |
| 三步口诀 | 改 → add → commit，才算存了档 |
| feat/fix/docs | commit 前缀：新功能/修 bug/文档 |
| restore | 三层撤销（工作区/暂存区/说明） |
| .gitignore | 不存档清单：能重新生成的都不进仓库 |
| safe.directory | 沙箱读 git 的单命令通行证（不写全局配置） |
| bundle | 把整个历史打包成一个文件（归档神器） |

## 第 7 节 分支：平行世界的时间线

第 1~6 节都在一条时间线上。**分支（branch）让你同时拥有多条时间线**：

```
main ──●──●──●──────────●──  ← 主线（稳定版）
            └──●──●──●──●    ← 分支（实验「圆角藻井」）
```

**白话**：主线继续走，实验在分支上折腾——**改砸了不影响主线，改好了再合并回来**。项目里的用法（虽然主力在 main 上开发）：不同主题分批 commit 本身就是「逻辑分支」。

**四个分支命令**：
```bash
git branch 实验名          # 开新时间线（从当前位置分叉）
git switch 实验名          # 跳过去
git switch main           # 跳回来
git merge 实验名           # 把实验成果并进主线
```

**什么时候必须分支**：改一个「可能改砸」的大东西（重构教材、换求解器）——**「不确定的探索上分支，确定的推进上主线」**。

▢ **你试试 6**：开一个分支，改点东西 commit，切回 main 看文件「恢复原样」，再 merge 回来。**亲眼看到平行世界合并，分支就懂了。**

⚠️ **新手常犯**：在主线上直接做实验改砸了——**git restore 救得了一处，救不了「改了一半混进主线」的乱局**。分支是实验的隔离病房。

## 第 8 节 远程与协作：GitHub 的完整图景

第 2 课之前只讲本地。**远程仓库（GitHub）= 档案柜的云端备份 + 协作大厅**：

```bash
git remote add origin <仓库地址>   # 登记云端档案柜
git push origin main               # 把本地历史推上去
git pull                           # 把云端的新历史拉下来
```

**push/pull 的本质**：**历史的同步**——两边都是完整历史，push 是「把我的新快照给你」，pull 是「把你的新快照给我」。

**万神殿的决策纪律**（8/10 决策）：**「项目做完再推」**——本地 commit 照常，GitHub 等完工（避免半成品被公开审阅的压力）。**「本地勤存档、云端择时机」是学生项目的稳健策略。**

**协作的黄金法则**（多人项目必用）：**先 pull 再 push**——别人可能刚推了新历史，你推之前要先把对方的拉下来合并。**「先同步再提交」避免冲突的第一步。**

▢ **你试试 7**：在 GitHub 建一个空仓库（不初始化），按 `remote add → push` 流程把你的练习仓库推上去。**看到网页上出现你的 commit 历史，远程就通了。**

## 第 9 节 万神殿 git 实战档案（33 commits 的完整病历）

把第 5 节的三个坑扩成完整病历（成书卷二的精华）：

| 病历 | 症状 | 病根 | 处方 |
| --- | --- | --- | --- |
| dubious ownership | `fatal: detected dubious ownership` | 沙箱用户 SID 与文件属主不同 | `git -c safe.directory="<路径>"` 单命令（**不写全局 config**） |
| 隐形字符 | 索引文件「看起来正常但 grep 不到」 | 写入 NUL 空字节（AI 产出的文档病） | 重写该行 + 抽查不可见字符 |
| 嵌套仓库 | legacy_v1 带自己的 .git | 旧项目整体归档 | 父仓库 .gitignore 排除 + bundle 双保险 |
| 路径漂移 | 8/14 项目搬家后命令全指向旧路径 | 目录迁移未同步文档 | README 路径修正 + 中继文档铁律（8/18 已修） |
| 行尾警告 | `LF will be replaced by CRLF` | Windows 行尾与 git 约定不同 | 无害警告，**不处理**（处理反而添乱） |

**读病历的方法**：每条按「症状→病根→处方」三段——**报错先对症状，症状对上直接抄处方**。这就是 Bug 模式库（卷八）的 git 版。

▢ **你试试 8**：把五个病历各用一句话复述，然后合上屏幕，说出「dubious ownership」的完整处方（含不写全局 config 的理由）。
