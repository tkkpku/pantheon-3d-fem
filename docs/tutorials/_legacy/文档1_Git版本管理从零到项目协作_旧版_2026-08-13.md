## 1. 前置理解：为什么必须用 Git？

### 1.1 没有版本管理的噩梦

想象一下这个场景（你一定见过）：

```
万神殿FEM_最终版.py
万神殿FEM_最终版_v2.py
万神殿FEM_最终版_改.py
万神殿FEM_最终版_不改了.py
万神殿FEM_最终版_真的最终版.py
万神殿FEM_最终版_导师意见修改.py
```

三个月后你完全不知道哪个是哪个，也不记得改了什么、为什么改。

### 1.2 Git 给你什么

> **Git = 代码的「时间机器」+ 「云同步」+ 「实验安全网」。**

| Git 能做的事 | 白话解释 |
|---|---|
| **记录每次修改** | 每次 `commit` 就像给代码拍一张快照，附上说明「我改了什么、为什么改」 |
| **回到任意历史版本** | 代码改崩了？一条命令回到三天前的状态 |
| **多分支并行开发** | 想试一个新算法又怕搞坏主代码？开个分支，不行就删，不影响主线 |
| **远程备份与协作** | 代码推到 GitHub，换电脑 `clone` 一下就全有了 |
| **追踪谁改了什么** | `git blame` 可以看到每一行代码是谁、什么时候、为什么写的 |

### 1.3 本项目用 Git 管理什么

- ✅ 所有 Python 源码（`geometry/`, `fem_solver/`, `post_process/`, `cases/`）
- ✅ 所有配置文件（`config/params.py`, `requirements.txt`）
- ✅ 所有文档（`docs/*.md`）
- ✅ 验证脚本（`verification/`）
- ❌ 虚拟环境（`.venv/`——每个人自己创建）
- ❌ 仿真结果文件（`.vtu`, `.msh`——太大，本地保存即可）
- ❌ Python 缓存（`__pycache__/`）

## 2. 核心概念 · 用白话一次讲清楚

### 2.1 仓库（Repository / Repo）

> **仓库 = 一个被 Git 管理的文件夹。**

在项目根目录运行 `git init` 后，Git 会在里面创建一个隐藏的 `.git/` 文件夹，用来存储所有版本历史。从此这个文件夹里的每一个变化，Git 都看在眼里。

**本项目的仓库**：`pantheon-3d-fem/`。一个全新的、独立的 Git 仓库，与旧项目（`pantheon/`）物理隔离。

### 2.2 提交（Commit）

> **Commit = 一次「保存操作」+ 「保存说明」。**

每次 commit 包含两样东西：
1. **快照**：此时所有被跟踪文件的状态
2. **消息**：一段文字说明这次改了什么

```bash
git commit -m "feat: 完成球壳参数化几何建模"
```

**类比**：像是写论文时按「另存为」并重命名为「论文_20260724_修改了第三章方法部分.docx」。Git 自动帮你做这件事，而且保存的是完整的差异记录。

### 2.3 工作区 → 暂存区 → 仓库（三棵树）

这是 Git 最核心但也最容易迷惑新手的模型。Git 在你的项目中有三个「区域」：

```
工作区 (Working Directory)     暂存区 (Staging Area)      仓库 (Repository)
───────────────────────       ─────────────────────       ────────────────
你正在编辑的文件              你决定「这次要提交的」       已永久保存的历史版本
    │                              │                          │
    │   git add                    │   git commit             │
    │ ──────────────────────────→  │ ──────────────────────→  │
    │   「选中这些修改」            │   「拍照 + 写说明」       │
```

**白话**：
- **工作区** = 你在 VS Code 里编辑的代码。改了什么 Git 都知道，但还没说要不要保存。
- **暂存区** = 你告诉 Git：「这些改动下次一起提交」。用 `git add` 把文件放进去。
- **仓库** = 已经永久保存的历史。用 `git commit` 完成。

**为什么多一个「暂存区」？** 因为有时候你改了三件事（修了一个 bug + 加了一个函数 + 改了注释），但想分两次 commit（一次修 bug，一次加功能）。暂存区让你可以选择「这次提交哪些」。

### 2.4 分支（Branch）

> **分支 = 一条独立的开发线。**

默认分支叫 `main`（或 `master`）。你可以从 `main` 分出新的分支，在上面实验，实验成功就合并回 `main`，实验失败就删掉分支——`main` 毫发无伤。

```
main:    ●──●──●──●──●──●  (稳定版本)
              ↘
feature:       ●──●──●  (实验性功能，做完后合并)
```

**本项目的分支策略**（简单版）：
- `main`：始终可运行的正确代码
- 功能开发直接在 `main` 上做（个人项目，不需要复杂分支策略）

### 2.5 远程仓库（Remote）

> **远程仓库 = 代码在 GitHub 上的备份。**

`origin` 是远程仓库的默认名字。`git push` = 把本地的 commit 上传到 GitHub。`git pull` = 把 GitHub 上的新 commit 下载到本地。

**本项目的远程仓库**：将在 GitHub 上创建 `tkkpku/pantheon-3d-fem`（与旧项目 `tkkpku/pantheon` 独立）。

### 2.6 一张图总结六大核心操作

```
工作区 ──git add──→ 暂存区 ──git commit──→ 本地仓库 ──git push──→ GitHub
  ↑                    ↑                       ↑                      │
  │                    │                       │                      │
  └────────────────────┴──── git checkout / git restore ──────────────┘
                                         (回退)
                        GitHub ──git pull──→ 本地仓库
```

## 3. 本项目的 Git 操作全流程

### 3.1 创建仓库 + 连接 GitHub

#### 步骤1：在 GitHub 上创建远程仓库

1. 浏览器打开 [https://github.com/new](https://github.com/new)
2. Repository name：`pantheon-3d-fem`
3. Description：`万神殿穹顶三维有限元分析 V2.0 — Gmsh + FEniCSx + PyVista`
4. 选择 **Private**（私有仓库，在项目完成前不公开）
5. **不要勾选** "Add a README file"、"Add .gitignore"、"Choose a license"（我们要推送本地已有的内容）
6. 点击 "Create repository"

创建后会显示一个页面，标题是 "Quick setup — if you've done this kind of thing before"。记下远程地址：
```
https://github.com/tkkpku/pantheon-3d-fem.git
```

#### 步骤2：本地初始化并连接远程

在 WSL Ubuntu 终端中：

```bash
# 进入项目目录
cd /mnt/c/Users/tan83/Desktop/pantheon-3d-fem

# 初始化 Git 仓库
git init

# 连接远程仓库（把 tkkpku 替换为你的 GitHub 用户名）
git remote add origin https://github.com/tkkpku/pantheon-3d-fem.git

# 验证远程连接
git remote -v
# 应该显示：
# origin  https://github.com/tkkpku/pantheon-3d-fem.git (fetch)
# origin  https://github.com/tkkpku/pantheon-3d-fem.git (push)
```

### 3.2 第一次提交（First Commit）

```bash
# 步骤1：看看当前状态
git status
# 会列出所有「未被跟踪」的文件（红色）

# 步骤2：把所有文件加入暂存区
git add -A
# -A = All，包括新建的、修改的、删除的

# 步骤3：确认一下暂存区里有什么
git status
# 现在文件应该是绿色（已暂存）

# 步骤4：提交
git commit -m "init: 项目初始化，创建基础目录结构"

# 步骤5：推送到 GitHub
git push -u origin main
# -u = 设置上游分支，之后只需要 git push 即可
```

### 3.3 日常提交流程（三件套）

这是你每天要做的最频繁的操作：

```bash
# 写了一些代码后...

# 1. 查看改了什么
git status                    # 看改了哪些文件
git diff                      # 看具体改了什么内容（按行显示）

# 2. 加入暂存区
git add geometry/dome_geometry.py    # 只加一个文件
# 或
git add -A                           # 加所有改动

# 3. 提交
git commit -m "feat: 实现五层藻井参数化几何建模"

# 4. 推送到 GitHub（一天结束时做一次）
git push
```

### 3.4 查看历史

```bash
# 简洁版：一行一个 commit
git log --oneline
# 输出示例：
# a1b2c3d feat: 实现五层藻井参数化几何建模
# e4f5g6h fix: 修正球面半径参数 R_inner = 22.03
# h7i8j9k init: 项目初始化，创建基础目录结构

# 详细版：包含作者、日期、完整消息
git log

# 看某个 commit 的具体改动
git show a1b2c3d    # a1b2c3d 是 commit 的哈希值（用 git log --oneline 查到）

# 看某个人（你自己）的所有提交
git log --author="你的名字"

# 图形化看分支历史
git log --oneline --graph --all
```

### 3.5 忽略已追踪文件的本地修改

有时候你临时改了某个文件做实验，但不想提交：

```bash
# 恢复某个文件到上次 commit 的状态
git restore config/params.py

# 恢复所有文件
git restore .
```

### 3.6 Git 认证（推送时输入密码的问题）

GitHub 不再支持密码登录 Git 操作。你需要用 **Personal Access Token (PAT)** 或 **SSH Key**。

**推荐方式：Personal Access Token**

1. GitHub → Settings → Developer settings → Personal access tokens → Tokens (classic)
2. Generate new token → Generate new token (classic)
3. Note：`pantheon-3d-fem`
4. Expiration：选一个较长的期限（如 90 days 或 No expiration）
5. 勾选 `repo`（完整的仓库访问权限）
6. Generate token → **复制并保存好！**（这个 token 只显示一次）

之后 `git push` 提示输入密码时，粘贴这个 token 即可。

**更方便的方式（免密）**：

```bash
# 把 token 缓存起来，避免每次输入
git config --global credential.helper store
# 下次 git push 输入 token 后，之后就不再问了
```

## 4. Commit Message 规范（本项目专用）

### 4.1 格式

```
<type>: <简短说明>
```

- `type` 和 `: ` 之间不要有空格
- 说明用中文或英文都可以，但要**简短**（不超过 50 个字符）
- 不要写「修改了一些东西」「更新代码」这种说了等于没说的话

### 4.2 Type 分类

| Type | 含义 | 示例 |
|---|---|---|
| `feat` | 新功能、新代码 | `feat: 实现球壳参数化几何建模（dome_geometry.py）` |
| `fix` | 修 bug | `fix: 修正密度梯度分段函数边界值` |
| `docs` | 文档（学习材料、README 等） | `docs: 完成文档3 FEM前置基础` |
| `refactor` | 重构（不改功能，但改代码结构） | `refactor: 将应力后处理逻辑提取到 stress_tensor.py` |
| `test` | 测试/验证 | `test: 添加网格收敛性自动化测试` |
| `config` | 配置/环境 | `config: 锁定 requirements.txt 版本` |
| `style` | 格式（空格、换行、注释） | `style: 统一 docstring 为 Google 格式` |
| `chore` | 杂务（不影响代码） | `chore: 清理 output/ 目录下的旧结果` |

### 4.3 好 vs 坏的 Commit Message

| ❌ 坏的 | ✅ 好的 |
|---|---|
| `update` | `feat: 添加28周期对称切片工具 symmetry_utils.py` |
| `fix bug` | `fix: 修正 Gmsh 布尔操作后藻井面法向不一致` |
| `修改参数` | `config: 更新密度分界纬度 12°/25°/40°` |
| `改了很多东西` | 这种情况应该**拆成多个 commit** |
| `feat: 完成了球壳参数化几何建模，包括五层藻井的布尔挖除，鼓座的环形墙体，基座建模，以及所有物理组的标记，还有网格局部加密，顺便修了一个边界条件施加错误的bug，然后还把参数文件的注释更新了` | 这应该拆成至少 3 个 commit！ |

### 4.4 同一个功能的修改归在一个 Commit 里

如果你在实现「藻井几何建模」这个功能时改了三个文件，那就是一个 commit：

```bash
git add geometry/dome_geometry.py geometry/assemble_model.py config/params.py
git commit -m "feat: 实现五层藻井参数化几何建模与布尔挖除"
```

不要在同一个 commit 里混入不相关的修改（比如「改了一下 README 的拼写」和「实现了一个新的求解器」不应该在一个 commit 里）。

## 5. `.gitignore` 配置

### 5.1 `.gitignore` 是什么

告诉 Git「这些文件/文件夹不要管」的规则表。放在项目根目录。

### 5.2 本项目的 `.gitignore`

创建 `/mnt/c/Users/tan83/Desktop/pantheon-3d-fem/.gitignore`：

```gitignore
# Python 虚拟环境
.venv/
venv/
env/

# Python 缓存
__pycache__/
*.py[cod]
*.egg-info/
*.egg

# 仿真输出（太大，本地保存）
output/meshes/
output/results/
output/figures/
output/data/
*.vtu
*.xdmf
*.h5
*.msh

# 系统文件
.DS_Store
Thumbs.db
*.swp
*.swo

# IDE 配置（如果你想分享 VS Code 配置就不要忽略）
.vscode/
.idea/

# Jupyter Notebook 检查点
.ipynb_checkpoints/

# 临时文件
*.tmp
*.bak
*temp*
```

### 5.3 为什么这些文件不提交

| 文件类型 | 不提交的原因 |
|---|---|
| `.venv/` | 每个开发者自己创建虚拟环境，`requirements.txt` 已锁定依赖版本 |
| `__pycache__/` | 自动生成的字节码缓存，换台机器会重新生成 |
| `output/*.vtu` | FEM 结果文件动辄几百 MB 到几 GB，Git 不适合存大文件 |
| `output/*.msh` | 网格文件也很大，且可以通过代码重新生成 |
| `.vscode/` | 每个人的编辑器配置不同，除非团队统一约定 |

## 6. 版本管理：打 Tag 标记里程碑

### 6.1 Tag 是什么

> **Tag = 给某个 commit 贴一个不可修改的标签（如 `v0.1`），标记「这个版本是重要的」。**

与 commit message 不同，tag 是专门用来标记里程碑的。比如「这个 commit 是几何建模完成的版本」。

### 6.2 本项目的 Tag 规划

| Tag | 对应阶段 | 含义 |
|---|---|---|
| `v0.1-geometry` | 阶段二完成 | 参数化几何建模完成，网格可导出 |
| `v0.2-elastic-solve` | 阶段三完成 | 线弹性求解体系完成，C1/C2 跑通 |
| `v0.3-stress-post` | 阶段四完成 | 三维应力解析与后处理完成 |
| `v0.4-shrinkage` | 阶段五完成 | 干缩荷载 + 裂缝分析完成 |
| `v1.0-full` | 阶段七完成 | 完整项目，全部文档齐备 |

### 6.3 Tag 操作

```bash
# 打轻量标签（推荐日常用）
git tag v0.1-geometry

# 打附注标签（推荐给重要里程碑，可以写说明）
git tag -a v0.1-geometry -m "阶段二完成：参数化几何建模，五层藻井+鼓座+基座全部建模"

# 查看所有 tag
git tag

# 推送 tag 到远程（tag 默认不随 push 一起发送）
git push origin v0.1-geometry

# 推送所有 tag
git push origin --tags

# 删除本地 tag
git tag -d v0.1-geometry

# 删除远程 tag
git push origin --delete v0.1-geometry

# 回到某个 tag 的状态（只读查看）
git checkout v0.1-geometry
```

## 7. 分支管理策略

### 7.1 本项目推荐策略：主干开发

因为是个人项目，推荐最简单的策略——**所有开发都在 `main` 分支上**。

```
main: ●──●──●──●──●──●──●──●
      init  feat  fix  feat  ...
```

### 7.2 什么时候用分支

当你想要实验一个「不确定能不能成功」的功能，不想影响 `main` 的稳定性时：

```bash
# 创建并切换到新分支
git checkout -b experiment-no-tension-concrete

# 在新分支上开发...
# ...各种实验...

# 如果实验成功，合并回 main
git checkout main
git merge experiment-no-tension-concrete

# 如果实验失败，直接删掉分支
git checkout main
git branch -d experiment-no-tension-concrete

# 如果分支已推送到远程，还需要删除远程分支
git push origin --delete experiment-no-tension-concrete
```

### 7.3 查看与切换分支

```bash
# 列出所有本地分支
git branch

# 列出所有分支（包括远程）
git branch -a

# 切换分支
git checkout main

# 创建并切换到新分支（一步完成）
git checkout -b new-feature
```

## 8. 常见错误与补救

### 错误 #1：commit message 写错了

```bash
# 修改最近一次 commit 的 message
git commit --amend -m "feat: 正确的commit信息"

# 如果已经 push 了（个人项目可以 force push）
git push --force-with-lease
```

> ⚠️ `--force` 是危险的。`--force-with-lease` 相对安全——如果远程有你不知道的新 commit，它会拒绝覆盖。

### 错误 #2：commit 漏了文件

```bash
# 把漏掉的文件加入暂存区
git add 漏掉的文件.py

# 追加到上一次 commit（不改 message）
git commit --amend --no-edit

# 如果要同时改 message
git commit --amend -m "新的commit信息"
```

### 错误 #3：`git push` 被拒绝

```bash
# 常见报错：
# ! [rejected] main -> main (fetch first)
# error: failed to push some refs to 'https://github.com/...'

# 原因：远程有你本地没有的新 commit（可能你在另一台电脑上 push 过）
# 解决：
git pull --rebase    # 拉取远程更新 + 把你的 commit 放在最上面
git push
```

### 错误 #4：想回到历史版本看看

```bash
# 查看某个 commit 的代码（只读模式）
git checkout a1b2c3d

# 看完后回到最新版本
git checkout main
```

### 错误 #5：想丢弃工作区的所有修改

```bash
# ⚠️ 危险操作！所有未提交的修改将永久丢失！

# 丢弃单个文件的修改
git restore config/params.py

# 丢弃所有修改
git restore .

# 同时清除未被跟踪的新文件
git clean -fd
```

### 错误 #6：不小心 `git add` 了不该提交的文件

```bash
# 从暂存区移除（但保留工作区的文件）
git reset HEAD 不该提交的文件.py

# 如果是 .gitignore 漏了，先更新 .gitignore，再执行上面命令
```

### 错误 #7：回退到某个历史版本（撤销错误的 commit）

```bash
# 方案A：保留工作区的改动（推荐）
# 撤销最近1个 commit，但改动保留在工作区
git reset --soft HEAD~1

# 方案B：连工作区的改动也丢弃（危险）
git reset --hard HEAD~1

# 回退到特定 commit
git reset --hard a1b2c3d

# 如果已经 push 了，需要 force push
git push --force-with-lease
```

### 错误 #8：merge 冲突

当两个分支修改了同一个文件的同一行时，Git 不知道该听谁的，就会产生冲突。

```bash
# 合并时看到：
# CONFLICT (content): Merge conflict in config/params.py
# Automatic merge failed; fix conflicts and then commit the result.

# 打开冲突文件，会看到这样的标记：
# <<<<<<< HEAD
# R_SPHERE = 22.03        # 你当前分支的值
# =======
# R_SPHERE = 22.00        # 要合并进来的分支的值
# >>>>>>> feature-branch

# 手动编辑：保留正确的，删除标记
# R_SPHERE = 22.03        # 保留这个

# 然后：
git add config/params.py
git commit -m "merge: 解决 params.py 冲突，保留 R_SPHERE=22.03"
```

> 作为个人项目，merge 冲突很少见。如果真的遇到，不要慌——Git 不会丢失任何代码，只是需要你做一次人工裁决。

## 9. Git 命令速查卡

### 日常高频（每天用）

| 命令 | 作用 |
|---|---|
| `git status` | 看改了什么 |
| `git diff` | 看具体改了什么内容 |
| `git add <file>` | 加一个文件到暂存区 |
| `git add -A` | 加所有改动 |
| `git commit -m "..."` | 提交 |
| `git push` | 推送到 GitHub |
| `git pull` | 从 GitHub 拉取 |
| `git log --oneline` | 看提交历史 |

### 回退与修复（偶尔用）

| 命令 | 作用 |
|---|---|
| `git restore <file>` | 丢弃工作区修改 |
| `git reset HEAD <file>` | 从暂存区移除 |
| `git commit --amend` | 修改最近一次 commit |
| `git reset --soft HEAD~1` | 撤销 commit 但保留改动 |
| `git checkout <commit>` | 回到历史版本看看 |

| 命令 | 作用 |
|---|---|

| `git branch -d <name>` | 删除分支 |
| `git tag <name>` | 打标签 |
| `git tag` | 列出标签 |
